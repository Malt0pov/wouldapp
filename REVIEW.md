# Код-ревью: WOULD VPN Client (WouldApp)

Проверено: `server.js` (814 строк), `index.html` (2955 строк), `README.md`, `.bat`, бинарники `WouldApp.exe` / `proxy_helper.exe` / `bin/*`, git-история.
Фактическое окружение на момент проверки: **sing-box 1.14.4**, **Node.js 26.13.0**, пользователь **не администратор**, в реестре остался `ProxyServer=127.0.0.1:2080` при `ProxyEnable=0`.

---

## Сначала — что работает

Чтобы не было впечатления, что «всё плохо»:

- **Конфиг sing-box, который генерирует `buildSingBoxConfig()` — корректный.** `bin/sing-box.exe check` даёт `exit 0` без единого warning'а и для proxy-, и для TUN-режима ([server.js:455](server.js#L455)). Формат DNS-серверов (`type` + `server`), `route.default_domain_resolver`, `action: sniff / hijack-dns`, `address` вместо legacy `inet4_address` — всё соответствует 1.14.4. `bin/active-config.json` тоже валиден. То есть «sing-box не стартует из-за конфига» — не ваш случай.
- Сервер слушает только `127.0.0.1:3005` ([server.js:806](server.js#L806)), mixed-inbound — тоже только loopback. Наружу не торчит.
- Парсеры ссылок (`vless://`, `trojan://`, `ss://`, `hysteria2://`) и JSON-подписок в целом рабочие; инъекции команд в `exec`/`reg` нет (строки не подставляются в команды).
- Логи в UI экранируются (`escapeHtml`), буфер ограничен 100 строками — XSS через логи не проходит.
- Визуально/UX (M3, темы, звук, анимации) сделано действительно аккуратно — это сильная часть проекта.

Дальше — проблемы, сгруппированные по критичности.

## КРИТИЧНО

### 1. Локальный API полностью без аутентификации → любой сайт может переключить VPN на свой сервер (MITM)

[server.js:659-795](server.js#L659-L795), в частности `/api/connect` [739-772](server.js#L739-L772), `/api/disconnect` [775-781](server.js#L775-L781), `/api/status` [663-671](server.js#L663-L671), `/api/parse` [711-736](server.js#L711-L736).

Ни токена, ни проверки `Origin`/`Host`, ни CSRF-защиты. При этом `/api/connect` принимает **произвольный** `outbound` из тела без валидации ([744-745](server.js#L744-L745)) и пишет его в конфиг sing-box ([527](server.js#L527)) — после чего **весь** трафик пользователя идёт через указанный сервер.

Как это эксплуатируется:
- `JSON.parse(body)` не зависит от `Content-Type`, а простой POST `text/plain` не требует CORS-preflight. Достаточно, чтобы запрос **дошёл** — ответ читать не нужно.
- В свежих Chromium/Edge запросы из публичной страницы в loopback режутся политикой PNA/LNA, но **в Firefox это не так**, и остаётся классический **DNS-rebinding** (`Host` не проверяется): страница получает same-origin доступ к `127.0.0.1:3005`.
- Итог: любой сайт/локальный процесс может тихо перенаправить трафик пользователя на узел атакующего, и `/api/status` при этом бодро покажет «подключено».

**Фикс:** одноразовый секрет, инжектируемый в `index.html` при отдаче + проверка в заголовке; жёсткая валидация `Origin`/`Host` (только `127.0.0.1:3005`); отклонять `Content-Type` ≠ `application/json`; для десктопа лучше named pipe с ACL вместо TCP-порта.

### 2. Path traversal + отдача всего каталога: чтение ключей и произвольных файлов

[server.js:783-794](server.js#L783-L794) — `req.url` никак не нормализуется, дальше `path.join(DIR, reqPath)` ([785](server.js#L785)).

Проверено экспериментом:
```
GET /../../../../../../Windows/win.ini  -> отдаётся C:\Windows\win.ini
GET /bin/active-config.json             -> отдаётся файл с реальными VLESS uuid/Reality ключами
GET /server.js, /.git/config            -> отдаются
```
Браузер сам нормализует `../` в `fetch`, поэтому через страницу файл-ридер не получить, **но любой локальный процесс/скрипт — читает любой доступный пользователю файл**. Плюс статика вообще не ограничена: `.git/`, `bin/`, конфиги с ключами лежат в открытом доступе по HTTP.

**Фикс:** `const safe = path.resolve(DIR, '.' + reqPath); if (!safe.startsWith(DIR + path.sep)) return 403;` + белый список отдаваемых файлов (отдельная папка `public/`), `bin/` и `.git/` не отдавать.

### 3. Системный прокси: нет бэкапа и восстановления, принудительное выключение при старте, «нет интернета» после сбоя

[server.js:31-60](server.js#L31-L60), [807](server.js#L807).

- `enableWindowsProxy` перезаписывает `ProxyServer`/`ProxyOverride`/`ProxyEnable`, **не сохраняя** прежние значения; `disableWindowsProxy` возвращает только `ProxyEnable=0`. Строки внутри `proxy_helper.exe` подтверждают: есть `SetValue` + `InternetSetOption`, но **нет** чтения/восстановления, нет работы с `AutoConfigURL` (PAC).
- `disableWindowsProxy()` вызывается **при каждом старте сервера** ([807](server.js#L807)) — то есть запуск клиента молча ломает корпоративный/личный прокси и PAC.
- Если процесс node/sing-box убили (Task Manager, крах, AV, закрытие окна Edge `--app`), `ProxyEnable` остаётся `1` на мёртвый `127.0.0.1:2080` → **у пользователя просто нет интернета** до ручной правки реестра или следующего запуска.
- Текущее состояние вашей машины — как раз след: `ProxyServer=127.0.0.1:2080`, `ProxyEnable=0`.
- Fallback-ветка через `reg add` ([38-44](server.js#L38-L44)) вообще не делает WinINet-broadcast, хотя комментарий выше обещает синхронизацию.

**Фикс:** сохранять все 5 значений (`ProxyEnable`, `ProxyServer`, `ProxyOverride`, `AutoConfigURL`, `AutoDetect`) до первого изменения и восстанавливать в `finally` / `process.on('exit')` / watchdog; не трогать прокси на старте; следить за PAC и предупреждать пользователя.

### 4. Жизненный цикл sing-box: гонки, «сирота» с занятым портом, лживый статус

[server.js:523-645](server.js#L523-L645).

- `singboxProcess` присваивается только через **600 мс** после spawn ([562](server.js#L562)), а `stopSingBox` убивает только то, что видит ([633](server.js#L633)). Два быстрых `/api/connect` → второй не видит первый, порт 2080 занят (`EADDRINUSE`), первый процесс становится **невидимым сиротой**: держит порт и wintun, exit-обработчик для него не срабатывает (`singboxProcess !== proc`, [552](server.js#L552)). Дальше подключение ломается до перезагрузки/Task Manager.
- `proc.kill('SIGTERM')` на Windows — это **TerminateProcess**, а не graceful shutdown: sing-box не успевает снять маршруты/TUN. Фиксированные паузы 300/600 мс — не синхронизация, а лотерея.
- `/api/status` считает `running` по `!!singboxProcess` ([665](server.js#L665)) → первые 600 мс и после любых сбоев статус врёт. Фронтенд `running` вообще не использует (см. п. 8).
- При падении/убийстве node дочерний sing-box не убивается (нет job object) → остаётся VPN без UI и с занятым портом.
- В TUN-фолбэке kill и spawn идут без ожидания exit ([576-587](server.js#L576-L587)) → та же гонка `EADDRINUSE`.

**Фикс:** фиксировать pid сразу после `spawn`, mutex/очередь на старт, ждать реальный `exit` (а не 300 мс), `taskkill /T /F` / Job Object, при старте искать и убивать сирот по порту 2080, периодический health-check sing-box.

### 5. Нет обработчиков `error`/`uncaughtException` → весь бэкенд падает, оставляя прокси включённым

[server.js:530-548](server.js#L530-L548) — `spawn` без `proc.on('error')`: если `bin\sing-box.exe` отсутствует/заблокирован антивирусом, Node выбрасывает необработанный `error` и завершается. Строки `proc.stdout.on(...)` ([538](server.js#L538)) от этого не спасают.

[server.js:787-790](server.js#L787-L790) — `existsSync`/`statSync` + `createReadStream().pipe(res)` без обработчика ошибки стрима: файл исчез между проверкой и чтением (TOCTOU) → снова необработанный `error` и падение процесса.

Глобальных `process.on('uncaughtException'/'unhandledRejection')` нет; аварийного выключения прокси тоже. Итог любого сбоя — сервер умер, sing-box сирота, прокси включён.

### 6. Kill Switch заявлен, но делает ровно наоборот

[README.md:30](README.md#L30) обещает Kill Switch. В коде: тумблер в UI пишет **только** в `localStorage` ([index.html:1869](index.html#L1869), [2775-2796](index.html#L2775-L2796), тост «Kill Switch активен (сеть защищена)» [2787](index.html#L2787)), а на сервер это значение никогда не уходит (в `/api/connect` уходят только `outbound/link/mode`, [index.html:2231-2235](index.html#L2231-L2235)). В конфиге sing-box нет ни одного `reject`/block-правила — только `sniff` и `hijack-dns` ([server.js:508-516](server.js#L508-L516)).

Хуже: при падении туннеля код **выключает** системный прокси ([server.js:550-557](server.js#L550-L557), [632](server.js#L632)) — то есть трафик гарантированно идёт напрямую с реальным IP. Это анти-kill-switch.

**Фикс:** либо реализовать на сервере (`route.rules` с `action: reject` + firewall-правило на 2080), либо убрать кнопку и пункт из README — сейчас это ложное чувство защиты в VPN-продукте.

## ВЫСОКО

### 7. Подписки: отключённая проверка TLS, SSRF, стабильный HWID и токен в логах

[server.js:318-365](server.js#L318-L365).

- `rejectUnauthorized: false` ([338](server.js#L338)) для **любого** HTTPS → MITM подписки в публичном Wi-Fi/у провайдера подсовывает свой узел, и пользователь сам подключается к атакующему.
- Редиректы (до 6) без allowlist хоста/схемы: `https → http` downgrade разрешён, редирект на `192.168.x.x` / `127.0.0.1` / `169.254.169.254` разрешён → **SSRF** через `/api/parse`.
- HWID = `md5(MachineGuid)` без соли, уходит в заголовках `x-hwid`/`x-device-id` **на любой** URL подписки ([324, 330-331](server.js#L324-L331), [228-240](server.js#L228-L240)) — стабильный идентификатор устройства третьей стороне, что противоречит разделу о приватности в README.
- Полный URL подписки с токеном пишется в лог ([386](server.js#L386)) и отдаётся через `/api/status` ([665-670](server.js#L665-L670)) → токен утекает в UI-терминал и любому локальному процессу.

### 8. TUN-режим физически не может работать при обычном запуске, и это скрывается от пользователя

- Манифест `WouldApp.exe`: `<requestedExecutionLevel level="asInvoker">` — **без** `requireAdministrator`, никаких `runas`/elevation в бинарнике нет. `Запустить WouldApp.bat` тоже поднимает node **без** повышения прав (проверено: текущая сессия не админ).
- Значит wintun-адаптер создать нельзя, sing-box падает, срабатывает авто-фолбэк на системный прокси ([server.js:573-626](server.js#L573-L626)) — но это только `warning` в логе.
- Фронтенд смотрит лишь на `res.success` ([2238-2244](index.html#L2238-L2244)) и **игнорирует** `res.result.mode`/`note`; бейдж режима остаётся «TUN (WINTUN)», статус — «Подключено». Пользователь уверен, что у него full-tunnel, а на деле только WinINet-прокси.
- Плюс режим не сохраняется: после перезагрузки `appState.mode` снова `proxy`, а `<select>` показывает дефолт (в `loadSettingsFromStorage` его нет).

### 9. IPv6-утечка и DNS-«изоляция» не реализованы

- TUN-inbound имеет **только** IPv4 `address: ['172.19.0.1/30']` ([server.js:471](server.js#L471)); `route.rules` не содержит reject для `ip_version: 6`. У пользователя с IPv6 от провайдера IPv6-трафик идёт мимо туннеля — сайты видят реальный IPv6. `strategy: prefer_ipv4` ([496](server.js#L496)) от этого не защищает. README:31 обещает защиту — её нет (`ipv6` в коде не встречается вообще).
- DNS: `remote-dns` объявлен с `detour: proxy`, но **нет `dns.rules`**, которые бы его выбирали, а `route.default_domain_resolver` указывает на `local-dns` = системный резолвер ([507](server.js#L507)). DoH/AdGuard из README ([32](README.md#L32)) отсутствуют: жёстко UDP `8.8.8.8` ([483-497](server.js#L483-L497)). Переключатель DNS в настройках ([1854-1858](index.html#L1854-L1858), `changeDns` [2798-2805](index.html#L2798-L2805)) — плацебо: пишет в localStorage, сервер его не читает.
- В режиме системного прокси `hijack-dns` приложений не видит: DNS уходит системно/провайдеру. «Прозрачный перехват 100% трафика» (README:19) в режиме по умолчанию неверен — WinINet-прокси уважают браузеры/Electron, но не игры, Telegram Desktop, службы и т.п.

### 10. Утечка при переключении узла (обещанный «Graceful Reconnect без утечек» наоборот)

`stopSingBox` сначала **выключает** системный прокси ([632](server.js#L632)), потом ждёт, убивает процесс, потом стартует новый. Между этим — 0.6–1 с трафика напрямую с реальным IP. Кроме того `selectServer` во время активного подключения ничего не переподключает: туннель остаётся на старом узле, а UI подписывает его именем нового ([index.html:2471-2481](index.html#L2471-L2481)).

### 11. Секреты и «взрослые» конфиги лежат в поставке

- `bin/active-config.json` содержит **живой** узел + uuid + Reality public_key/short_id и никогда не удаляется и не обнуляется ([527](server.js#L527)).
- `bin/test-dns.json`, `bin/test-dns-tun.json`, `bin/test-lookup.json` содержат реальные UUID тестового узла (значения не привожу).
- `.gitignore` закрывает `bin/`, но `WouldApp-Setup.exe` **закоммичен** в репозиторий (76 МБ), и в его строках присутствует `active-config.json` — то есть с большой вероятностью инсталлятор уезжает к пользователям вместе с dev-конфигами. Стоит проверить содержимое payload'а и ротировать ключи.
- Обратное следствие: из свежего клона репозитория `node server.js` (инструкция README) **не запустится** — `bin/` (sing-box, node, wintun) не в git.

### 12. Нет лимитов на размер тела/ответа и на частоту запросов

[server.js:712-714](server.js#L712-L714), [740-742](server.js#L740-L742), [351-353](server.js#L351-L353) — `body += chunk` без ограничения, тело подписки копится целиком, `/api/parse` может сделать 6 запросов по 12 с. Любой локальный процесс (или rebinding-страница) валит бэкенд по памяти/времени.

## СРЕДНЕ (в основном фронтенд и «честность» UI)

### 13. Телеметрия — мок, а не данные

- Скорость Download/Upload — `Math.random()` ([index.html:2353-2362](index.html#L2353-L2362)), график рисуется по этим же случайным числам. README:21-23 обещает «живую телеметрию 60 FPS, мониторинг скорости в реальном времени».
- Пинг: `testAllPings` прибавляет случайные ±4 мс к случайно сгенерированному стартовому пингу ([2517-2528](index.html#L2517-L2528), [2594](index.html#L2594)). README:26 обещает «Real TCP Handshake / HTTP 204» — такого бэкенда нет вообще (в server.js 5 эндпоинтов, `/api/ping` отсутствует).
- «Статистика сессии» `totalDownloaded/Uploaded` никогда не инкрементируется ([2144-2145](index.html#L2144-L2145), [2807-2814](index.html#L2807-L2814)) → всегда «0.0 MB». Сортировка серверов по пингу (README:27) тоже не реализована.

### 14. Состояние подключения не синхронизируется с бэкендом

`updateLogs` дёргает `/api/status` каждые 2.5 с, но берёт только `data.logs`, игнорируя `data.running` и `data.mode` ([index.html:2896-2906](index.html#L2896-L2906)). Если sing-box упал или его убили — UI продолжает показывать «Подключено» бесконечно. Отключение тоже асинхронно-лживое: сначала рисуется «Отключено», потом отправляется запрос, ошибка молча глотается ([2253-2261](index.html#L2253-L2261)).

### 15. Гонка по кнопке питания при подключении

`toggleVpn` в состоянии `connecting` уходит в ветку «отключить» (условие только `status === 'disconnected'`) — двойной клик по кнопке питания вызывает `/api/disconnect` посреди старта, а сервер через 600 мс всё равно включит прокси и пометит процесс живым. Кнопка не блокируется во время установления соединения.

### 16. Плацебо-настройки (важно для доверия к продукту)

Держатся только в `localStorage`, на работу не влияют: Kill Switch, «Сворачивать при закрытии»/трей, «Автозапуск с Windows», «Автоподключение» (`autoConnect` нигде не читается), выбор DNS, «Сбросить счётчик» (сбрасывает нули). Для VPN-клиента это опасная категория багов: пользователь считает, что включил защиту.

### 17. Google Fonts CDN в UI VPN-клиента

[ index.html:14-16](index.html#L14-L16) — иконки Material Symbols грузятся с `fonts.googleapis.com`. Ровно у целевой аудитории клиента Google часто недоступен: иконки превращаются в текст («power_settings_new», «vpn_lock»), интерфейс разваливается. Шрифты нужно локально бандлить (при 76 МБ инсталляторе это не проблема).

### 18. Мелкие UI/UX-баги

- Глобальный `user-select: none` ([67](index.html#L67)) — нельзя скопировать логи, IP, текст ошибки; поддержке и пользователю это мешает.
- Порт в списке серверов захардкожен: «Адрес сервера: ip**:443**» ([2456](index.html#L2456)), хотя реальный порт может быть 30584.
- Мок-серверы по умолчанию: `198.51.100.22` (TEST-NET-2), `185.220.101.44` (известный Tor-exit) и др. ([2116-2121](index.html#L2116-L2121)); «Подключить» на них ведёт в модалку импорта — выглядит как баг.
- `refreshPublicIp` спамит snackbar при каждом вызове, а «proxied» — это просто факт наличия процесса, а не проверка IP ([server.js:694](server.js#L694)); ip-check ходит по **plain HTTP** к `ip-api.com` ([677-678](server.js#L677-L678)) — ответ можно подменить, UI покажет фальшивый «защищённый» IP/страну.
- В `drawSpeedWave`/`renderServerList` есть непроэкранированные подстановки (`s.flag`, `s.ping`), а `escapeHtml` не экранирует кавычки — не критично (данные локальные), но лучше закрыть.
- Ключи и `outbound` хранятся в `localStorage` в открытом виде ([2151](index.html#L2151)) в профиле `%LOCALAPPDATA%\WouldApp\Profile` — переживают удаление приложения.

3. **В git лежат бинарники без исходников**: `WouldApp.exe`, `Uninstall.exe`, WebView2 DLL, инсталлятор 76 МБ. Воспроизвести сборку нельзя, ревьюить нельзя, обновить WebView2 — тоже. C#-обёртку и установщик стоит вынести в отдельный репозиторий с исходниками.
4. **Две конкурирующие точки входа**: `.bat` (node + Edge `--app`) и `WouldApp.exe` (node + WebView2). В `.bat` `--app-id=WouldAppVPN` — несуществующий app id, Edge его игнорирует; закрытие окна Edge не останавливает ни node, ни sing-box, ни прокси.
5. `EADDRINUSE` → `process.exit(0)` ([server.js:797-804](server.js#L797-L804)): второй экземпляр тихо умирает, а `/api/disconnect` из одного окна рвёт VPN во всех.
6. MIME-fallback: неизвестное расширение (в т.ч. `.exe`) отдаётся как `text/html` ([788](server.js#L788)).
7. `execSync` в `getMachineHwid` ([231](server.js#L231)) блокирует event loop на первой загрузке подписки.
8. Нет `package.json`, тестов, CI; нет версионирования/`build`-скриптов. Для проекта с сетевым ядром и управлением системным прокси это дорого обходится.
9. В `bin/` навсегда оставлены `test-*.json` — их стоит убрать из дистрибутива.
10. `proxy_helper.exe`/`sing-box.exe`/`WouldApp.exe` без цифровой подписи — SmartScreen и AV будут ругаться, а для VPN-клиента это критично для доверия.

## Что советую чинить в этом порядке

1. **Path traversal + whitelist статики** (п.2) — 10 минут, закрывает утечку ключей/файлов.
2. **Токен + валидация `Origin`/`Host`/`Content-Type` на `/api/*`** (п.1) — закрывает CSRF/DNS-rebinding/MITM.
3. **Бэкап и восстановление реестра прокси, не трогать прокси на старте, аварийный cleanup** (п.3) — закрывает «после клиента нет интернета» и корпоративный прокси.
4. **Жизненный цикл sing-box**: pid сразу, mutex, ожидание exit, обработчики `error`/`uncaughtException`, health-check (п.4, п.5) — закрывает сирот и ложный статус.
5. **TLS-проверка подписок, allowlist редиректов, маскирование токена в логах, лимиты тела** (п.7, п.12).
6. **Убрать/реализовать обещанное**: Kill Switch (п.6), IPv6 (п.9), DNS/DoH (п.9), пинг (п.13), мок-скорости (п.13), QR/TUIC из README, плацебо-тумблеры (п.16).
7. **TUN**: либо UAC-манифест/elevation, либо честно писать «требуются права администратора» и пробрасывать фактический режим в UI (п.8).
8. Фронтенд: синхронизация статуса с `/api/status` (п.14), блокировка кнопки при `connecting` (п.15), локальные шрифты (п.17), `user-select` (п.18).

### Оговорки

- `server.js`/`sing-box run` я не запускал специально: старт сервера меняет реестр прокси и сеть, а `run` с живыми ключами небезопасен. Runtime-выводы (порядок снятия маршрутов wintun после TerminateProcess, поведение WinINet с PAC) помечены как теоретические; всё, что помечено как проверенное — воспроизведено на этой машине (path.join, парсер HTTP Node, `sing-box check`, строки бинарников, состояние реестра, `IsAdmin=False`).
- Живые учётные данные из `bin/active-config.json` и `test-*.json` в отчёт не выносились. Их стоит считать скомпрометированными: файл отдаётся по HTTP без авторизации и лежит в дистрибутиве — лучше перевыпустить ключи.
